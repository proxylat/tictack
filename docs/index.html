Overview

One-way file synchronization, system image backup, and third-party software scheduler for Windows 10/11 and Linux.

Two paired binaries

TicTack was built to stay at zero CPU when nothing is changing while matching the safety guards and feature set of closed-source backup suites. The repository ships two dependency-light binaries — TicTackSv (file sync, low-latency remote sync, and job scheduler) and Corpus.exe (Windows 10/11 block and volume imager):

1. File synchronization (TicTackSv) Runs as a Windows service, a Linux systemd unit, or from the CLI. Watches user folders and mirrors changes in real time or after a configured delay with version history and deletion archiving. → 2. Low-latency remote sync (TicTackSv) Pulls live changes from remote machines or VMs over encrypted TTRM v1 TCP (TLS 1.2/1.3 + mutual PSK) with an OS-sandboxed --remote-agent and push change stream. → 3. Software scheduler (TicTackSv jobs:) Schedules and sandboxes external backup tools like Corpus.exe, restic, and rclone inside Windows JobObjects, gated by pre-flight disk-fit and local network stability checks. → 4. System image backup (Corpus.exe) Standalone Windows 10/11 block-level imager (invoked directly or scheduled by TicTackSv). Captures live NTFS volumes and 512e/4Kn physical disks via VSS into a deduplicated chunk store or dynamic VHDX and WIM images. →

Design goals

  • Do one thing well and obey least astonishment: TicTack handles one-way file synchronization, block-level volume imaging, and scheduled job execution. If a setting in your configuration file is misspelled or duplicated, startup fails immediately and names the bad key instead of running with silent defaults.
  • Zero-CPU idle, flexible sync timing, and EcoQoS scheduling: You can mirror changes in real time, after a configurable debounce delay, on a periodic polling interval, or as a one-shot CLI pass. Between file events, the service sleeps on OS kernel notifications at 0% CPU. When a sync or backup runs, optional EcoQoS efficiency mode and low I/O priority keep background transfers off foreground CPU cores so active work or games do not stutter.
  • Continuous Data Protection (near-zero RPO) and GFS retention: Live file changes mirror after your configured delay, keeping your Recovery Point Objective (RPO, the amount of recent work you could lose if a drive fails) near zero. Overwritten and deleted files rotate into separate history (.versions) and deleted-items (.archive) folders with independent Grandfather-Father-Son (GFS) retention (keep_daily, keep_weekly, keep_monthly, keep_yearly, keep_last, keep_within, --clean-all) and .pin locks.
  • Crash consistency, sparse preservation, and power-loss recovery: Existing backup files are never overwritten in place. New data streams to a temporary file beside the target, flushes to physical disk along with the parent directory entry, and swaps in atomically. Thin-provisioned virtual machine disks (sparse files) copy only their allocated data blocks without inflating to their full virtual size, and interrupted large transfers resume from where they stopped.
  • Fail fast, fail loud, and circuit-break anomalies: A pre-read check catches file lock and permission failures before copying begins. Pre-flight disk fit checks verify the entire backup fits on the destination drive, and passive local network checks verify routing, link health, packet error deltas, and local gateway latency before cloud jobs start. Mass-deletion holds and sliding-window churn circuit-breakers pause ransomware-like spikes during a cooling-off period and write warning files to your Desktop.
  • Sandboxed job orchestration and low-latency remote sync: Scheduled third-party tools (restic, rclone, Corpus) run inside OS process sandboxes (Windows JobObjects that block UI popups and terminate orphan child processes on timeout). Built-in remote LAN and VM transfers run over authenticated TCP inside a Low-Integrity or restricted OS token locked to the destination folder.
  • Encryption scope: Remote VM sync (TTRM v1) is encrypted in transit by default (TLS 1.2/1.3 + mutual PSK). Local fsync mirrors are plain 1:1 files by design — encryption at rest is a major security responsibility and is intentionally not implemented in TicTack for now. For encrypted storage, use OS volume encryption (BitLocker / LUKS), schedule restic / rclone crypt via jobs:, or use Corpus's external per-pack encrypt: / decrypt: commands ({input} / {output}, e.g. age or gpg).

Limitations and constraints

No macOS support and Corpus Windows-only scope
TicTack targets Windows 10/11 and Linux; there is no macOS service, watcher, or snapshot integration. Corpus is currently Windows-only because it relies on Windows VSS (vssapi.dll), NTFS raw $MFT, $Bitmap, and USN parsing, and VHDX/WIM APIs.
No built-in local encryption at rest
Remote VM sync (TTRM v1) is encrypted in transit by default (TLS 1.2/1.3 + mutual PSK), but TicTack's local fsync mirror writes plain 1:1 files by design. Encryption at rest is a major security responsibility and is intentionally not implemented in TicTack for now — use OS volume encryption (BitLocker / LUKS), schedule restic or rclone crypt via jobs:, or use Corpus's external per-pack encrypt: / decrypt: commands ({input} / {output}, e.g. age or gpg).
One-way authority (Source to Destination)
TicTack treats your source folder as the single source of truth and mirrors changes in one direction (Source → Destination). It does not perform bidirectional multi-master sync or two-way merge conflict resolution, ensuring a modified or corrupted backup drive never overwrites your live working files.
No %VAR% or ~ expansion in configuration paths
Never write %USERPROFILE%, %HOME%, or ~ in config.yaml. Services run under LocalSystem or root, so expanded variables would point at the wrong profile. Always write full paths (C:\Users\Alice\Documents, /home/alice/Pictures) or use Windows [VolumeLabel]\path syntax.

Quickstart

Get running fast: install the Windows 10/11 service or Linux systemd unit, or run from the CLI.

TicTack quickstart (File sync & scheduler)

Switch tabs below to inspect service setup on Windows 10/11 or Linux, interactive CLI commands, or a unified config.yaml combining file sync, Corpus volume imaging, restic, and rclone:

REM Run cmd.exe as Administrator (supports default, --jit, or --aot)
copy service\win\config_win.yaml.example service\win\config.yaml
service\win\build-service.bat --jit

REM Restart service after config edits
sc stop TicTackSv && sc start TicTackSv
# Copy config and publish to /opt/tictack with systemd unit enabled
cp service/linux/config_linux.yaml.example service/linux/config.yaml
cd service/linux && ./build-service.sh

# Check status and follow live logs
sudo systemctl status tictack
journalctl -u tictack -f
# Interactive foreground watch + scheduled jobs
TicTackSv --cli

# Single sync pass over all sources, then exit
TicTackSv --once

# Independent GFS pruning for .versions and .archive
TicTackSv --forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --keep-yearly 1
TicTackSv --archive-forget --keep-daily 14 --keep-monthly 3
sources:
  - paths:
      - "C:\\Users\\Alice\\Documents"
      - "C:\\Users\\Alice\\Projects"
    destination: "[Backup-Disk]\\Mirror"
    debounce_seconds: 10
    sync:
      verification: date_and_size
      durability: full
      min_free_gb: 20
      strict_fit_check: true
      versioning:
        path: "[Backup-Disk]\\Mirror\\.versions"
        keep_daily: 7
        keep_weekly: 4
        keep_monthly: 6
        keep_yearly: 1
      deletion:
        mode: archive
        path: "[Backup-Disk]\\Mirror\\.archive"
        keep_daily: 14
        keep_monthly: 3

jobs_defaults:
  sandbox: true
  timeout_minutes: 60

jobs:
  - name: corpus-system-image
    time: "02:00"
    command: "Corpus.exe --config C:\\ProgramData\\TicTack\\config_corpus.yaml --image --volumes C:,D: --name nightly"
  - name: restic-repo
    time: "03:00"
    command: "restic -r [Backup-Disk]\\Restic backup {source}"
  - name: rclone-cloud
    time: "04:00"
    net_check: true
    command: "rclone sync [Backup-Disk]\\Restic s3:my-offsite-bucket/restic"

Corpus quickstart (Windows 10/11 volume imaging)

CLI (TicTack)

Every TicTackSv command-line flag: sync passes, GFS pruning, pins, holds, and remote agent.

Service & sync modes

Start the Windows service, interactive CLI watcher, one-shot sync, or config validator.

FlagDescription

Remote sync

Built-in encrypted TCP synchronization (TTRM v1) with ephemeral TLS, mutual PSK auth, and OS sandboxing.

Architecture & protocol (TTRM v1)

TicTack includes a built-in, zero-dependency binary TCP synchronization protocol (TTRM v1) so a host can pull live file changes from a remote machine or VM without exposing SMB/CIFS shares. The agent (TicTackSv --remote-agent) exports a single read-only directory tree (remote_sync.root) over an encrypted, mutually authenticated channel while running inside an OS sandbox.

Handshake & binary framing

TTRM v1 handshake, framing, and sandbox layers 
  Client (SyncPipeline + RemoteFileAccessor)               Server (TicTackSv --remote-agent)
  ──────────────────────────────────────────               ─────────────────────────────────
  1. TCP Connect (NoDelay, 4 MiB socket buffers) ────────► IP Allowlist (allow_ip:) & Ban Check
                                                           (5 auth/frame/traversal errors = 60s ban)

  2. TLS 1.2 / 1.3 Handshake (SslStream)       ◄────────► Ephemeral ECDSA P-256 X.509 Cert
     (tls: true by default; single-record                  (CN=TicTackRemote, generated in-memory
      coalesced ArrayPool frames)                           at agent startup; zero CA files needed)

  3. Mutual HMAC-SHA256 PSK Challenge-Response
     (pskKey = SHA-256(psk | psk_env | psk_file))
                                               ◄─────────  Auth Challenge: [WireVer=1 (2B) | sNonce (32B)]
     cNonce = CSPRNG(32B)
     cMac   = HMAC-SHA256(pskKey, "TTRM-C" || sNonce || cNonce)
     Send [cNonce (32B) | cMac (32B)]          ─────────►  FixedTimeEquals(cMac, expected)
                                                           sMac = HMAC-SHA256(pskKey, "TTRM-S" || cNonce || sNonce)
     FixedTimeEquals(sMac, expected)           ◄─────────  Auth Ok: [sMac (32B)]

  4. Binary Frame Stream (12-byte LE header: [Magic "TTRM" 0x5454524D (4B) | Op (4B) | Len (4B)])
     • Control Pool: List(2), Stat(3), ReadChunk(4), Hash(5), ReadFile(7), HashPrefix(8)
     • Push Stream:  Subscribe(6) ◄─────────────────────── ChangeEvent(0x80000001) from OS Watcher

Encryption, PSK & OS sandbox layers

Security LayerImplementation
Transport encryption (tls: true)Uses SslStream with Tls12 | Tls13 and an in-memory ephemeral ECDSA P-256 (nistP256) self-signed certificate generated at startup. Frames coalesce [12B Header | Metadata | Payload] into one rented ArrayPool<byte> buffer so each frame emits a single TLS record. When tls: false on trusted loopback/WireGuard links, SendGather uses zero-copy scatter/gather I/O (WSASend / writev)
Mutual PSK authentication (psk: / psk_env: / psk_file:)Derives a 32-byte key via SHA-256(secret) and runs a 3-way challenge-response with 32-byte CSPRNG nonces (serverNonce, clientNonce) and domain-separated HMAC tags ("TTRM-C", "TTRM-S") verified via CryptographicOperations.FixedTimeEquals. Proves both peers hold the PSK and prevents MITM against the ephemeral TLS certificate
Wire framing & resource capsEvery frame carries magic 0x5454524D ("TTRM"), a 32-bit operation code, and a 32-bit length capped at MaxFrameBytes = 16 MiB (file chunks stream in 4 MiB windows). Remote SHA-256 (Op.Hash and append-proof Op.HashPrefix) offloads hashing to the agent so unchanged files never cross the network
Root path jail & auto-banEvery requested relative path is canonicalized via Path.GetFullPath and verified to reside strictly under remote_sync.root. Any traversal attempt (UnauthorizedAccessException), malformed/oversized frame (InvalidDataException), or bad HMAC increments the per-IP failure counter; 5 failures ban the IP for 60 seconds
Windows OS sandbox (RemoteSandbox)Strips all process token privileges (AdjustTokenPrivileges(disableAllPrivileges: true)), lowers the token to Low Mandatory Integrity (S-1-16-4096) under sandbox_level: low (or restricted), and assigns a Windows JobObject with ACTIVE_PROCESS = 1, KILL_ON_JOB_CLOSE, and UILIMIT_ALL
Linux kernel sandbox (RemoteSandbox)Sets prctl(PR_SET_NO_NEW_PRIVS), sets RLIMIT_NPROC = 0 (forbids fork/exec), and enforces a Landlock LSM ruleset restricting kernel filesystem access to read-only beneath remote_sync.root (plus read/exec on /usr, /lib, /lib64, /etc) with zero write access anywhere on the system

Consistency groups and I/O freeze

When an application and its database span multiple volumes or disks (for example, application state on C: and database files on D:), snapshotting volumes one after another risks state skew. Corpus prevents this with three guards:

  • Multi-volume atomic VSS snapshot sets (--volumes C:,D:): Adds all target volumes to a single StartSnapshotSet / DoSnapshotSet freeze window and links the resulting manifests with a shared ConsistencyGroupId.
  • Fail-closed VSS writer status verification (strict_vss_writers: true): Calls GatherWriterStatus after PrepareForBackup and DoSnapshotSet. If a participating writer (such as SQL Server or Hyper-V) reports FailedAtFreeze or any error state, Corpus aborts instead of recording an inconsistent snapshot (set strict_vss_writers: false to downgrade to warning-only).
  • Pre-freeze and post-thaw hooks (pre_freeze / post_thaw): Brackets DoSnapshotSet in a try/finally block so non-VSS databases (PostgreSQL, MySQL, SQLite, custom daemons) can flush and freeze I/O for only the few seconds it takes VSS to commit the shadow copy.

GFS retention and garbage collection

Corpus manifests are self-contained (incremental generations remain restorable after their parent generation is pruned, and depth-1 delta chunks automatically pin their base chunks). Mark-sweep garbage collection retains the union of:

  • keep_last: N most recent generations
  • keep_within_days: all generations newer than N days
  • keep_daily / keep_weekly / keep_monthly / keep_yearly: newest generation in each calendar bucket (yyyy-MM-dd, ISO week yyyy-Www, yyyy-MM, yyyy)
  • pin: explicitly listed generation numbers
cmd 
REM Preview GC plan with GFS overrides
Corpus.exe --gc --dry-run --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --keep-yearly 1

REM Execute GC plan
Corpus.exe --gc --confirm --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --keep-yearly 1

Exclusions (--exclude / exclude:)

Exclusions are NTFS-name based and match against volume-relative paths (without a drive letter, e.g. Users\Bob\Desktop), case-insensitively:

FormMeaning
--exclude DesktopEvery directory named Desktop at any depth plus its subtree (bare file names match at the volume root only)
--exclude Users\Bob\DesktopExactly that volume-relative path (file or directory)
  • No drive prefix: --exclude C:\Users\Bob\Desktop matches nothing because volume-relative paths do not include C:.
  • No %VAR% expansion inside Corpus.exe: Pass expanded paths or let cmd.exe expand %USERPROFILE% (and remember to strip the drive letter).
